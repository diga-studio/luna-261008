# backup-integrity-repair

备份完整性修复库（TypeScript，供上层调用）。面向离线备份设备：同一个坏块可能影响多个文件版本，终端补传正确数据后，设备既要修复共享块，也要解除对应的损坏记录；进程在任意一步被强制终止后，重新打开仓库即可自动恢复，无需重新扫描整个仓库。

## 存储布局

纯本地文件（无数据库、无网络、无监听端口）：

```
<repo>/
  manifest.jsonl        版本清单：每行一个版本 {"id","blocks":[["<sha256>",<len>],...]}
  report.json           当前损坏报告（整体原子替换）
  blocks/<aa>/<hash>    块正文，按 SHA-256 寻址，相同哈希只有一份
  staging/              修复补传的暂存区
  journal/              修复日志（崩溃一致性保证）
```

## 能力

```ts
import { BackupRepairStore } from "backup-integrity-repair";

const store = await BackupRepairStore.open("/path/to/repo");

// 1. 导入固定版本清单与初始块数据（仅一次；初始块允许缺失或损坏）
await store.import(versions, blocks);

// 2. 完整校验：检查所有被引用块的存在性、长度、SHA-256，原子替换报告
const report = await store.verify();

// 3. 提交单块修复：逐段到达的字节，长度与 SHA-256 匹配清单后才生效
await store.repairBlock(hash, chunkStream);

// 4. 读取当前损坏报告
const current = await store.getReport();
```

- 文件按 4 MiB 切块，末块允许更短；块可跨版本共享，也可在同一版本中重复引用（报告中不重复计数）。
- 报告包含损坏块（哈希、期望长度、受影响版本）与仍受损的版本列表。
- 被拒绝的补传（长度不符 / 哈希不符 / 未被清单引用）抛出 `RepairRejectedError`，不改变原有块与报告。
- 修复成功后，该块的全部共享引用同时恢复；一个版本仍有其他坏块时继续出现在受损版本中。
- 同一块的正确补传可重复提交，结果与成功修复一次一致。

## 崩溃一致性

所有操作在库内部串行执行。修复按以下顺序落盘（每步均 fsync）：

1. 补传数据写入暂存文件并校验长度与 SHA-256（不符则丢弃，状态不变）；
2. 写修复日志 `journal/<hash>.json`；
3. 暂存文件原子 rename 为正式块文件；
4. 报告原子替换，解除该块的损坏记录；
5. 删除修复日志。

重新打开仓库时自动恢复：若发现修复日志，且对应块已是正确内容，则补齐报告更新；否则说明崩溃发生在块提交之前，丢弃暂存、保持原块与原报告。两种情况下都不会留下半写块，也不会出现块与报告只更新一侧的状态；已返回成功的修复不会回退。恢复只读取清单、报告、修复日志和至多一个块的正文（≤ 4 MiB，远低于 16 MiB 上限），不依赖重新执行完整校验。`store.recoveryBlockBytesRead` 可读取本次恢复的正文读取量。

完整校验只有在全部结束后才原子替换报告；中断的校验不会暴露半份报告，此前的完整报告保持可用。

## 构建与测试

只需要 Node.js（>= 18）：

```sh
npm install
npm test
```

测试覆盖：多版本共享且重复引用的两个坏块逐个修复与重组校验、补传写一部分即终止、块文件与报告仅一侧完成更新时的进程终止与恢复、已确认修复的持久性、完整校验中断、单块恢复的正文读取量上限。
